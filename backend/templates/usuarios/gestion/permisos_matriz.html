{% extends "base.html" %} {% comment %} ========================================================================== MATRIZ DE PERMISOS — /roles/permisos/ (HU-04) Permisos como FILAS, roles como COLUMNAS. Se eligió esta disposición porque la pregunta habitual del administrador es "¿quién puede validar fichas?", y así se responde leyendo una fila en vez de abriendo tres pantallas. La estructura que se recorre (grupos -> filas -> celdas) la arma la vista en Python. La plantilla no decide nada: solo escribe HTML. El motivo es que el lenguaje de plantillas no puede resolver "¿tiene el rol 2 el permiso 7?" sin inventar filtros propios, y preparar los datos en la vista es más simple y se puede probar. Las casillas se dibujan a mano en vez de usar {{ form.permisos }}, que produciría una lista vertical por rol e impediría la disposición en matriz. El atributo name= viene de form.nombre_campo_html, así que plantilla y formulario no pueden desincronizarse. ========================================================================= {% endcomment %} {% block titulo %}Roles y permisos{% endblock %} {% block contenido %}

Por qué el Administrador no se puede editar

El rol Administrador concede todos los permisos por definición del negocio, igual que el superusuario técnico. Si se le pudieran quitar, bastaría un clic para dejar el sistema sin nadie capaz de repararlo desde la aplicación y habría que intervenir la base de datos a mano. Es la misma salvaguarda que impide deshabilitar al último administrador activo.

Permisos de módulos aún no construidos

El catálogo incluye acciones sobre fichas, operativos y reportes, que corresponden a historias de usuario todavía no implementadas. Están modeladas de antemano para que, cuando esas pantallas existan, la autorización ya esté decidida. Un permiso sin pantalla que lo compruebe no autoriza nada por sí solo.
